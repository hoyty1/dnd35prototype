# Combat actions: the action catalog

Part of [ARCHITECTURE.md](../ARCHITECTURE.md). The plan is `docs/designs/action_catalog_batch13.md` ("Architecture", "End state"). The catalog lists every combat action in scope once, with its PHB Table 8-2 cost and provocation, and gives each one shared executor that the PC panel and the AI both reach. Step 3 built the skeleton over the finished cores as a pure move: no rule changed, and every scenario trace hash stayed the same. Step 6 (also a pure move) routed the AI's action calls through it and added the legal set in shadow mode. Step 9 (a pure move) made one move executor for both sides (section "The move executor" below).

## The executor rules

- `CanStart` and `CanExecute` roll no dice, log nothing and change nothing.
- `Execute` pays through `ActionCosts.TryPay` or through the core it wraps, and fills the outcome.
- An executor never continues the UI (`ShowActionChoices`, `AfterAttackDelay`, `EndActivePCTurn`, `DelayedEndActivePCTurn`) and never reads `IsControllable`, `ActivePC` or `IsPlayerTurn`. Whose choices they are is the context's `Source`. `ActionCatalogTests` scans every file under `Combat/Actions/Executors` for these names.
- A callback core (the cast core with the UI decider, the maneuver core) is waited on through its flag, and the loop stops when the combat ends. The cast executor reads the cast context's own outcome when a dialog re-entered the cast and replaced its done callback.
- A Delegating executor delegates to a live caller's entry point with that caller's prelude, never to a raw core alone: the attack entries run `NPCPerformAttack` (through `ActionCore_NpcAttack`) for the AI and `PerformPlayerAttack`'s rules (the direct-attack gate, the ward break) for the player unless the caller passes its own `AttackSequenceRequest`; stand-up applies its callers' gate before `ResolveStandUpFromProne`; overrun computes the path's AoOs (`CheckForAoO`) when the request has none.
- An executor whose core logs its own refusal sets `RefusalLogged` (the cast core, the move core, the 5-foot step, lay on hands, wild shape, bardic music, maintain concentration, the AI attack and stand-up), so the PC runner does not log it twice.

## The runners

- **`RunPlayerAction(ctx)`** sets `Source = Ui`, runs the executor and then applies the entry's `UiAfter`: `ShowChoices` shows the panel; `AttackDelay` runs `AfterAttackDelay` (it ends the turn when nothing is left); `EndTurn` ends it, after `UiAfterSeconds` when given. A refusal logs `"<name> cannot <action>: <reason>."` (one trailing period, nothing for an empty reason, nothing when the core logged it) and shows the panel. A downed actor ends the turn; an ended combat does nothing. An entry with `UiAfter` `None`, or a run whose core continues the UI itself (`CoreOwnsUi`: the UI cast decider's finish continuation, which a held-charge delivery through a UI `SpellCastRequest` also reaches), owns every follow-up, its refusal, cancel and downed actor included: the runner adds nothing, so no line is logged twice and no turn ends twice (CORE-012). A refusal before the executor runs always logs and shows the panel.
- **`RunAIAction(ctx, o)`** sets `Source = AI` and is yielded as a nested enumerator. It pre-checks `CanExecute` only for Extracted and New entries, where a refusal spends nothing; a Delegating entry's core owns its refusals, so routing a call through it refuses nothing new. Before the executor it builds the actor's legal set and compares the pick (`ActorActionSet.Check`): a disagreement is `Debug.Log("[ActionSet] <actor> picked <id> outside the legal set: <reason> (<bar>)")`, never a combat-log line (combat-log lines are hashed), and the pick runs either way (shadow mode, C8); a throw while building the set is logged and ignored. Each disagreement (and each throw) is also recorded in `ActionSetShadow`, which the scenario harness clears per job and writes into `summary.json` (`actionSet`), since fast mode drops Log-level lines (`docs/TESTING.md` 3.4). The check runs only where `ActionSetShadow.Enabled` (the editor and development builds). `RunPlayerAction` refuses an AiOnly entry (its executor serves the AI until step 18).
- **`RunAIActionInline(ctx, o)`** is `RunAIAction` with the runner's and the executor's enumerators inlined (`InlineAction`, two levels), for a wrapper that used to return the core's enumerator: the core's own yields reach the caller unchanged, so no frame is added. **`RunAIActionNow(ctx)`** drains the run at once for a synchronous call site (a cast through `RunCastSync`, a maneuver with `NoWait`, a 5-foot step, lay on hands, wild shape, bardic music, maintain concentration, a held charge, the monster specials); an executor that waits there is logged and its waits skipped.
- **`ResolveActionProvocation(actor, AoOProvokingAction, decider, outcome)`** is the one AoO loop for non-movement actions. The threateners come from `ThreatSystem.GetActionAoOProvokers` (the footprint, living foes that can still make an AoO); with none it returns at once. The decider confirms first (`ConfirmActionProvocation`); then each foe takes its AoO until the actor drops, with a `CombatLogHelper.Buff` line for each. It never ends a turn.
- **`ConfirmActionProvocation(actor, action, name, threateners, decider, outcome)`** is the prompt alone, for a core that takes its own AoOs (the stand-up core). A cancel sets `Cancelled` and the refusal; Unavailable refuses without a cancel; a prompt torn down without an answer (`ShowActionChoices`, `CancelMovementSelection` and the encounter reset clear it without calling `OnCancel`) counts as a cancel, so the wait never hangs; a combat end sets `CombatEnded`.
- Both runners read the action economy before and after the run (`ActionCosts.Take`, `SpentSince`) to fill `Spent`.

**The AI's routing (step 6, a pure move).** Every AI action call goes through `RunAIAction` with its entry, and each wrapper keeps its exact behaviour:
- the GameManager wrappers: `NPCPerformAttackForAI` (the full attack entry when more than one step may be taken and the full-round action is free, else the attack entry; `NpcAttackRequest` keeps the step cap), `NPCExecuteChargeForAI` (charge or bull-rush-charge with `ChargeRequestForAI`, then the NPC pacing wait), `MoveCharacterAlongComputedPathForAI` and `ExecuteWithdrawMovementForAI` (a `MoveRequest` since step 9: the caller's own request, or `MoveSpend.None` for the four-argument form, the caller paying), `TryTakeFiveFootStepForAI`, `TryStandUpFromProneForAI`, `NPCExecuteOverrunForAI` (`OverrunActionRequest` with the caller's outcome; the combat-end check stays the wrapper's), `NPCExecuteBreathWeaponForAI`;
- the NPC cores in `GameManager.NPCTurns.cs`: the casts (`TryNPCPerformSpellCast`, area, summon and hold, through `RunAICastAction` and the cast entry), the maneuvers (`TryNPCSpecialAttackIfBeneficial`, the maneuver's entry with `NoWait`), the summon's moves and attack and the step chooser's 5-foot step (now through the wrappers);
- AIService's `TryExecuteRangedSpecialAttack` (spittle or ranged special) and `TryExecuteEngulf` (their cores are `ExecuteRangedSpecialAttackCore` and `ExecuteEngulfCore`), its maintain-concentration and held-charge delivery calls; lay on hands (`TryNPCLayOnHandsTurnForAI`), bardic music (`TryNPCBardicMusicTurnForAI`, the choice as the `Variant`, its targets as `CoreRequest`) and wild shape (`TryNPCWildShapeTurnForAI`).
The compulsion controllers reach the same wrappers. Not routed: the NPC reload (`ExecuteReload`, PcOnly until step 12), the grapple turn's actions and the turn-start triggers (auras, frightful presence: step 19).

**The move executor (step 9, a pure move).** `GameManager.ExecuteMoveAction(MoveRequest)` (its one attempt record is `MoveRequest.Attempt`, made by the executor when null) (`Combat/Actions/Executors/GameManager.MoveAction.cs`) runs every PC and AI move and withdraw, in order: the shared legality `MovementService.CanStartMovement` (a refusal is logged "X cannot move: reason.", sets `MoveAttempt.Refused` and spends nothing; a PC's spend refusal keeps its old wording, "X has no action available for movement." or "X cannot complete Withdraw: reason.", `MoveRequest.PcRefusalText`); the path (the request's own, the PC's click, or one found to its destination within the budget: none means nothing moves and no refusal); the spend before the walk (`MoveSpend.ExecutorOwned`: the withdraw's `TrySpendWithdrawAction`; `MoveSpend.MoveAction` unless `MoveQuirk.AiSpendsAfterWalk`, converting the standard action when `AllowConvertStandard`); the walk (the PC's per-step loop, a private `ExecuteMovement(MoveRequest, ...)` overload so a combat ended by a PC dropped on its own move still reports the frames [..., `EvaluateCombatEnd`, `ExecuteMovement`] in `ScenarioTrace.CallerFrames`, or the segment walker `ExecutePathWithMovementAoOs` under `MoveQuirk.AiSegmentLoop`); and the after-walk spend under `AiSpendsAfterWalk` (also with no path under `AiSpendsWithoutPath`, and skipped for a dropped mover under `AiNoSpendIfDropped` or after the combat end under `AiNoSpendIfCombatOver`). It never continues the UI. `MoveActionExecutor` builds a request when the context has none by the context's side: a Ui context (the harness's Ui `Step.Action`) gets the PC's own (`UiRequestFor`: the click's path search, `MoveRequest.ForUi`, paid before the walk with the standard action converted; `rules/movement-step-action-converts-standard-ui`), an AI one `DefaultAiRequest`; `RunPlayerAction` marks the PC busy (`PlayerSubPhase.Animating`, path preview hidden) while a move or withdraw entry runs, as the click path's `ExecuteMovement` does, so the harness's Ui step waits for the walk. Since step 9 the PC's move also passes the runner's `CanExecute` and the executor's `CanStartMovement`: the Move and Withdraw buttons already asked it, but the overrun dialog's Normal Move (`OverrunSystem.ExecuteNormalMovementPath`, gated only by `CanUseOverrun`) now refuses a PC that may not move (a failed Grease Balance check this round, a condition that stops movement, pinned or grappling, speed 0; RAW, PHB p.142-144, p.237) with "X cannot move: reason." where it used to walk. No budget scenario reaches it.
- `MoveRequest.ForUi(pc, path, provoked, withdraw, seconds)`: no quirk bit, the standard action converts, the combat-end check `PCMovement.Incapacitated` for a PC dropped on the way. `GameManager.ExecuteMovement(pc, path, isWithdraw, provokedAoOs)` builds it and runs the move or withdraw entry through `RunPlayerActionInline`; the entry's UiAfter (ShowChoices) and the runner give the PC's old tail: the action panel, or the turn's end for a dropped PC.
- `MoveRequest.ForAI(mover, destination, seconds, spend, attempt)` sets every AI bit (`MoveQuirk.AiDefault`, the AIService routines' rule); `ForAIWithdraw` pays its own action. The modifiers record each site's after-walk test: `ConvertingStandard()` (the compulsion moves), `SpendingEvenIfDropped()` (charmed, confused, suggested: spent whenever not refused), `SpendingAfterCombatEnd()` (the summon and search moves in `GameManager.NPCTurns`, which test only the mover), `SpendingOnlyIfStarted()` (the catalog's own AI pick, `MoveActionExecutor.DefaultAiRequest`, which AiOutOfReach reaches).
- The sites (the plan's 20 spend sites, 24 move calls at 798fdb4): 11 in AIService, 3 in NPCTurns, 3 charmed, 2 confused, 1 frightened flee and 1 suggested move pass `MoveSpend.MoveAction` and dropped their own spend; AiOutOfReach's move uses the entry's default request; two pass `MoveSpend.None` and pay themselves: the frightened run (its full-round action) and the held charge's touch move (AIService `TryDeliverHeldChargeTurn`: its after-walk test is `ThreatSystem.IsMoverIncapacitated`, which also counts the Unconscious condition). No site reads the action economy between its walk and its spend. `MovementLegalityTests.TestMoveSiteClassification` pins the classification.
- Step 10 (AI-076, D3) deletes the two spend bits so every move is spent when it starts; the drop and combat-over bits go with them.

**The harness.** `Step.Action(actionId, target, variant)`, `Step.ActionAt(actionId, x, y)` and `Step.ActionItem(actionId, itemId, target)` (or `ScenarioBuilder.Action(actor, round, actionId, ...)`) take any catalog entry: a Scripted or AI-run actor runs it through `RunAIAction`, a Ui actor through `RunPlayerAction`.
