# Testing

This doc covers how to check changes in this project: the headless compile check, the hand-rolled static test suites under `Assets/Scripts/Tests`, the Play-mode scenario harness, and in-game manual testing. It replaces `Assets/Scripts/Tests/README.md`, `Assets/Scripts/Tests/AidAnother_ManualTestScenarios.md` and `Assets/Scripts/Tests/Combat/SleepSpell_ManualTestScenarios.md`.

The suite results dated 2026-10-07 (section 3.2) and the scenario-harness runs of 2026-10-07 (sections 3.4 and 3.5) come from Play-mode and edit-mode runs through the Unity MCP; other claims about runtime behavior come from reading the code. Known test problems are tracked with stable IDs in [issues/TST.md](issues/TST.md) (index: [KNOWN_ISSUES.md](KNOWN_ISSUES.md)); IDs from other areas point to the matching `issues/<PREFIX>.md` file.

## 1. Testing levels at a glance

| Level | How to run | What it catches | What it misses |
|---|---|---|---|
| Compile check | `bash tools/compile_check.sh` (about 5-7 s, no Editor needed) | C# compile errors in all of Assembly-CSharp, test code included | Runtime behavior, scene/asset problems, Editor-folder code, player-build-only errors |
| Static suites | The committed runner `Tests.Runner.StaticSuiteRunner`: menu **Tools > DND Tests**, or `RunFromCommand` through the Unity MCP (section 3); an edit pass, then a Play pass | Rule regressions in mechanics that have a suite, compared against the known-failures baseline `tools/tests/static-suites.json` | Anything without a suite (section 2.2); suites that pass on a bug |
| Scenario harness | `Tests.Scenarios.ScenarioHarness.Start` through the Unity MCP in a fresh Play session (section 3.4), or `ScenarioHarness.QueueFresh` from edit mode for one fresh Play session per filter (section 3.5) | Whole fights in the real game loop with seeded and forced dice: invariant violations, combat ends the game misses, soft locks, per-scenario rule expectations, same-seed determinism; the AI-vs-AI soak against DMG random encounters (section 3.5) adds per-side action counts as an AI-depth baseline | The PC path for AI-run party members (they take the NPC turn path); prompts other than the AoO confirmation, the counter-trip prompt, the full attack's 5-foot step prompts (always skipped), the grapple natural-attack menu and the Haste chooser; anything no scenario or invariant looks at |
| Manual testing | Play `Assets/Scenes/MainScene.unity`, use presets and the F12 panel (section 4) | UI flow, targeting, AI, end-to-end combat | Anything you do not look at |

### Compile check

`tools/compile_check.sh` reuses the compiler response file Unity last generated (`Library/Bee/artifacts/*/Assembly-CSharp.rsp`), keeps its defines and references, replaces the source list with the current `Assets/**/*.cs`, and runs Unity's bundled Roslyn (`F:/Unity/<version>/Editor`, override with `UNITY_DIR`). The DLL goes to a temp dir; `Library/` is not touched. `VERBOSE=1` prints every warning.

- Requires that Unity has opened the project once on this machine (so the `.rsp` exists). If packages or scripting defines change, the `.rsp` is stale until Unity regenerates it.
- Compiles with the Editor defines (`UNITY_EDITOR`, `ENABLE_LEGACY_INPUT_MANAGER`, LangVersion 9.0), so it cannot detect code that only breaks a player build (for example `using UnityEditor` outside `#if UNITY_EDITOR`).
- Skips every path containing `/Editor/` (there are none today), analyzers and source generators. It does not import assets or create `.meta` files.
- Baseline at 0dd8e76: `exit=0 errors=0 warnings=508`, of which 479 are CS0618 (obsolete API: mostly the string overloads of `ItemDatabase.CloneItem`/`ItemDatabase.Get`, then `FindObjectOfType`). Treat any error, or a jump in the warning count, as a regression.

Run it after every code change. All test files compile into the game assembly, so a broken test breaks the game build too.

## 2. Static test suites

### 2.1 How a suite is written

There is no test framework: no `com.unity.test-framework` in `Packages/manifest.json`, no `.asmdef`, no `[Test]` attributes. A suite is a plain class:

- `public static class <Name>Tests` in namespace `Tests.<Folder>` (`Tests.AI`, `.Character`, `.Classes`, `.Combat`, `.Feats`, `.Inventory`, `.Magic`, `.Maneuvers`, `.Mounts`, `.Services`, `.Utilities`). Exceptions in the global namespace: `CraftingSystemTests`, `Phase5IntegrationTests`, `RodTests`.
- Entry point `public static void RunAll()` (97 suites). It resets private static `_passed`/`_failed`, logs a header such as `====== SLEEP SPELL RULES TESTS ======`, calls the database `Init()` methods (all idempotent), runs `private static void TestXxx()` methods, and logs a summary such as `====== ... Results: N passed, M failed ======` (the format varies; the runner reads the counters directly, section 3). It returns nothing.
- Most suites have their own private `Assert(bool condition, string testName, string detail = "")` that logs `  PASS: <name>` with `Debug.Log` or `  FAIL: <name> <detail>` with `Debug.LogError` (example: `Tests/Combat/SleepSpellRulesTests.cs:37-49`). Variants (`AssertEqual`, `AssertTrue`, ...) follow the same pattern. Exception: `Phase5IntegrationTests` logs `FAIL:` with plain `Debug.Log`, so its failures do not show under the Console Error filter.
- 19 suites also expose a snake_case alias such as `class_level_feature_progression_test() => RunAll()` (`Tests/Character/ClassLevelFeatureProgressionTests.cs:15`). Nothing calls them.
- Tests build characters with `new GameObject()` + `AddComponent<CharacterController>()` + `CharacterController.Init(stats, pos, null, null)` + `InventoryComponent.Init(stats)`, clean up with `Object.DestroyImmediate` in `finally`, and reach private members through `System.Reflection` (19 test files, about 60 `GetMethod`/`GetField`/`GetProperty` reflection calls; TST-006).

- **`Tests.Runner.StaticSuiteRunner`** (`Assets/Scripts/Tests/Runner/StaticSuiteRunner.cs`, all inside `#if UNITY_EDITOR`, not in an `Editor/` folder so the compile check covers it) discovers and runs every suite. Section 3 describes it.

### 2.6 Pitfalls

IDs refer to [issues/TST.md](issues/TST.md) unless another prefix is given.

- **GameManager singleton.** 14 suites call `new GameObject().AddComponent<GameManager>()`. `GameManager.Awake` (`_Core/GameManager.cs:483-490`) schedules `Destroy` on the new object and returns early if `GameManager.Instance` already exists (in MainScene, SceneBootstrap creates one), so the test instance has no services; tests patch `_conditionService` in by reflection. In a scene without a GameManager the test instance becomes `Instance`, runs the full Awake, and `Instance` is left pointing at a destroyed object after cleanup (nothing resets it). `DispelMagicRulesTests.cs:244-273` takes a different branch depending on which case applies. Results can depend on the scene (TST-007, TST-005).
- **SquareGrid.Instance is overwritten.** `SquareGrid.Awake` sets `Instance = this` unconditionally (`Grid/SquareGrid.cs:25-28`). Six suites add their own SquareGrid, so after a run `SquareGrid.Instance` points at a destroyed grid. Code that falls back to it (`CharacterController.CurrentGrid`, `CharacterController.cs:11974`, `GameManager.cs:5182, 5387, 5473`) is affected. The runner puts `SquareGrid.Instance` back after each suite; a suite called by hand does not. Restart Play mode after running suites before playtesting (GRID-010, [issues/GRID.md](issues/GRID.md)).
- **Static state.** Databases, `ItemDatabase` registrations and `UnityEngine.Random` state are static and persist for the whole Play session (Enter Play Mode Options are off, so a new Play session resets them). Suites that call `Random.InitState(seed)` never restore the previous state, and `DiceService.Roll` uses `UnityEngine.Random` directly with no seeding API (TST-010); a test can instead force single dice through `ScenarioHooks.RollFilter` (section 3.3) and must clear it in `finally`. The runner seeds each suite and restores `Random.state` after the pass, restores `GameManager.Instance` and `SquareGrid.Instance` when a suite replaced them, and destroys root GameObjects a suite left behind. It does not reset static databases, registrations or other static fields, so suites can still affect each other and the game in the same Play session.
- **GameSettings auto-creates a GameObject.** `GameSettings.Instance` (`_Core/GameSettings.cs:22-38`) creates a `GameSettings` object if none exists. `CharacterStats.ApplyPendingLevelUp` reads it to pick the HP mode (default Roll, random), so level-up HP in tests such as `MulticlassSkillRulesTests` is random. Left Ctrl+H (`Utilities/DebugCommands.cs`, self-bootstrapped via `RuntimeInitializeOnLoadMethod`) cycles Roll/Average/Maximum in Play mode.
- **Rings, rods and wondrous items are not in ItemDatabase after `ItemDatabase.Init()` alone.** `SceneBootstrap.cs:1036-1063` calls `RingDatabase.Init`, `WondrousItemDatabase.Init`, `RodDatabase.Init` and then `RegisterAllRingsInItemDatabase` / `RegisterAllInItemDatabase`. A test that looks those items up through `ItemDatabase.Get` must do the same.
- **Play mode is required** for some suites: `AreaEffectManager.Instance` calls `DontDestroyOnLoad` (`Spell/AreaEffects/AreaEffectManager.cs:13-21`), which only works in Play mode; `ConcealmentRulesTests` uses it directly (indirect use from other suites not checked). `CharacterController.Init` uses the `SpriteRenderer` that `Awake` creates, and `Awake` does not run on `AddComponent` in edit mode, so every suite that calls `Init` throws `NullReferenceException` in edit mode (TST-009).
- **Assigning `controller.Stats` instead of calling `Init`.** In Play mode `Awake` has already added a `ConditionManager` with no stats, so conditions applied to such an actor are dropped without a word; in edit mode the `CharacterStats` fallback path runs instead of `ConditionManager` (TST-029). An actor whose `GridPosition` is never set stands in the same square as every other such actor, and `CharacterController.Attack` refuses the attack as out of range. Build actors with `TestHelpers.CreateCharacter` (or `Init`) at explicit adjacent positions.
- **Exceptions inside a suite.** Only 3 test files contain a `catch`, so one exception skips the rest of that suite and its summary line. The runner catches it, records the exception type, message and three stack frames, still reads the suite's counters, and goes on with the next suite.
- **Reflection breaks at runtime, not compile time.** Renaming private members such as `GameManager._conditionService`, `_activeSummons`, `_mirrorImageStates`, or `CharacterController.EstablishGrappleWith` breaks tests silently. About 18 test files make about 48 `GetMethod`/`GetField`/`GetProperty` calls. Grep `Assets/Scripts/Tests` for the member name before renaming (TST-006).
- **Namespace shadowing.** Inside any `Tests.*` namespace, `Inventory` resolves to the namespace `Tests.Inventory`; write `global::Inventory` for the class (TST-011).
- **CharacterStats constructor order** is `..., str, dex, con, wis, intelligence, cha, ...` (WIS before INT, `Character/Stats/CharacterStats.cs:3345`). Use named arguments.
- **Static Play passes after scenario-harness fights.** A static Play pass run in the same Play session as harness fights once reported false `GrappleDamageRulesTests` regressions (34 unexpected "NPC melee sequence" / "AI stopgap" failures) that a fresh session did not show; the cause is unknown (TST-035). The runner adds a warning when the harness started fights earlier in the session (`ScenarioRunner.JobsStartedThisDomain`). Run static Play passes in a fresh Play session after harness runs.
- **Tests ship in player builds.** No asmdef or `#if` guard; the three MonoBehaviour suites appear in the Add Component menu (TST-013).

### 2.7 Writing a new suite

1. Create `Assets/Scripts/Tests/<Folder>/<Name>Tests.cs` with `namespace Tests.<Folder>` and `public static class <Name>Tests`.
2. Copy the `RunAll`/`Assert` skeleton from `Tests/Combat/SleepSpellRulesTests.cs:12-49`: reset counters, header log, database init (that file calls `RaceDatabase`/`ClassRegistry`/`ItemDatabase`/`SpellDatabase.Init()` directly; `TestHelpers.EnsureCoreDatabasesInitialized()` also covers `FeatDefinitions`), test calls, summary log.
3. Build characters with `TestHelpers.CreateCharacter(...)` using named arguments; set `GridPosition` directly.
4. Wrap each test body in `try/finally` and destroy everything you created, including any GameManager or SquareGrid.
5. Prefer public API. If reflection is unavoidable, `Assert` that the `MethodInfo`/`FieldInfo` is not null instead of silently returning a default.
6. Do not add `Assert(true, ...)` placeholders. If something cannot be tested yet, log a warning that does not count as a pass.
7. If you seed `UnityEngine.Random`, save `Random.state` first and restore it in `finally`.
8. Run the compile check, then run the suite with the runner (`RunFromCommand("filter=<Name>Tests")`, section 3) and paste its line from `static-<mode>.txt` into your change notes. Add an entry for the suite to `tools/tests/static-suites.json` (`needs`, and any known failures with their issue IDs), or the runner reports it as NEW.

## 3. Running suites

`Tests.Runner.StaticSuiteRunner` (`Assets/Scripts/Tests/Runner/StaticSuiteRunner.cs`) is the committed runner. The whole file is inside `#if UNITY_EDITOR`, so it does not ship in player builds; it is not in an `Editor/` folder, so `compile_check.sh` compiles it.

**Entry points.**

- Menu **Tools > DND Tests > Run Static Suites (current mode)**, **List Static Suites** and **Write Proposed Baseline**. Each logs its summary to the Console.
- From a Unity MCP `CommandScript`: `Tests.Runner.StaticSuiteRunner.RunFromCommand("<options>")` returns a summary of at most about 4,000 characters (verdict, totals, the non-passing suites, file paths). `ListSuites()` lists every discovered suite with its `needs` and reports NEW and MISSING suites. `Run(StaticRunOptions)` returns the full `StaticRunReport`. The types are public because the MCP's script assembly cannot see internal members.
- `StaticSuiteRunner.RanInPlayModeThisDomain` is true once a Play pass ran in this domain (it resets when Play mode is entered again).

**Discovery.** Every non-nested type in Assembly-CSharp whose name ends in `Tests` and declares a parameterless `public static void RunAll()` (preferred) or `RunAllTests()`, sorted by full name. That gives 112 suites today (109 `RunAll`, 3 `RunAllTests`). `ServiceTestRunner` and `DungeonEncounterTableExamples` do not end in `Tests` and are not run.

**Mode gating.** Each suite's `needs` comes from the baseline (`play`, `edit`, `either`, `unknown`; a suite missing from the baseline counts as `unknown`).

- A Play pass runs `play`, `either` and `unknown` suites. It records whether a scene `GameManager` existed (`sceneGameManager`) and warns when it did not.
- An edit pass runs only `edit` suites: CauseFear and Scare, which fail in Play mode because of TST-007, and the 10 suites that build actors without `Init` and lose their conditions in Play mode (TST-029). In edit mode those 10 run the `CharacterStats` condition fallback, not `ConditionManager` (section 2.5), so they do not cover the game's condition path until TST-029 moves them back to `play`. It runs inside a temporary additive scene that becomes the active scene, then restores the previous active scene and closes the temporary one without saving. It never saves a scene.
- `all=true` ignores the gate and baseline skips; suites run in the wrong mode are marked `modeMismatch`.

**Refusals** (verdict `REFUSED`, nothing runs, only `static-<mode>.txt` is written, so the JSON of an interrupted pass stays resumable): Unity is compiling; scripts have compile errors; Unity is entering or leaving Play mode; `STALE_CODE`; a resume that does not match (see `after=`); or, in an edit pass, the temporary scene cannot be created (for example while an untitled scene is open). `STALE_CODE` means the loaded code may not be what is on disk: a `.cs` file under `Assets` is newer than both `Library/ScriptAssemblies/Assembly-CSharp.dll` and the last edit-mode script import, or the dll was rebuilt after the domain loaded. Whether Unity recompiles an edit made during Play mode depends on the per-user preference *Script Changes While Playing*, so the runner checks instead of assuming. A file whose timestamp changed without a content change (for example after `touch`) is not reimported by `AssetDatabase.Refresh()` and keeps tripping the check; once a refresh compiled nothing, pass `allowStaleCode=true`.

**Isolation, per suite.**

- Suite logs are captured by swapping `Debug.unityLogger.logHandler` (plus `Application.logMessageReceived` for engine messages) and are not echoed to the Console unless `echo=true`, so Console Error Pause does not stop a run. With `echo=true` the suites' FAIL `LogError` lines reach the Console, and Error Pause can leave Play mode paused after the call; the summary then shows `paused=true`, and `ExitPlaymode` still works.
- Exceptions are caught; the result records the type, message and three stack frames, and the run goes on.
- When the seed is not 0, `UnityEngine.Random` is seeded with `seed XOR FNV-1a(full name)` before the suite. The state from before the pass is restored at the end.
- New root GameObjects in the loaded scenes (and, in Play mode, the DontDestroyOnLoad scene) are counted in `leakedCount`, named in `leaked` (first 10) and destroyed (`cleanupLeaks=false` keeps them).
- Known game leaks (`KnownLeakIssues`, by root name) are destroyed too but reported as one aggregated `knownLeaks` entry per name, for example `Name x12 (ISSUE-ID, destroyed)`. The list is empty since UI-001 was fixed on 2026-10-08: before, every combat log call orphaned 50 `PooledLogMsg` lines at the scene root (588 in one FlankingReach run). A stray `PooledLogMsg` root now counts as an ordinary leak.
- Lazily created singletons that keep a static `Instance` are kept and listed under `singletonsCreated` (with `xN` when more than one): `AreaEffectManager`, `WindEffectManager`, `ExperienceCalculator`, `GameSettings`, `DebugCommands`.
- `GameManager.Instance` and `SquareGrid.Instance` are put back if the suite replaced them (TST-007, GRID-010); the result lists them under `restored`.
- Files that appear in the project root during a suite are listed under `strayFiles`. Only names on the runner's allowlist (`phase5_6_test_results.txt`, the old Phase5 dump) are deleted; any other file is marked `(kept)`, because it may not belong to the suite.
- The runner does not reset static databases, registrations or other static fields.

**Counts.** The runner reads the suite's private static `_passed`/`_failed` fields (also after a throw). Without them it uses the last `N passed, M failed` line, else it counts PASS/FAIL marker lines. `noSummary` flags a suite with counters but no summary line that did not throw.

**Failure labels.** Each captured line that matches `[Tag] FAIL:`, `[FAIL]`, `❌` or `✗` becomes a label: the tag and markers are stripped and duplicates merged, at most 60 kept. `failureCounts` (parallel to `failures`) records how many FAIL lines carried each label, so an assertion text used twice (RapidShot's "Rogue should have Rapid Shot feat") counts twice. Other error logs and exceptions are counted as `errorLogCount` with 5 samples; they are informational only.

**Options** (space-separated `key=value` tokens):

| Option | Meaning |
|---|---|
| `filter=A,B` | Run only suites whose full name contains one of the entries (case-insensitive) |
| `all=true` | Ignore the mode gate and baseline skips |
| `seed=N` | Seed base; the default is the baseline's `seed` (20261007). `seed=0` does not seed the suites, so they continue from the session's `Random.state`; the runner restores that state after every pass, so repeated `seed=0` passes in one Play or editor session start from the same state and repeat each other. For a spread, sweep explicit seeds (`seed=1`, `seed=2`, ...), as the 2026-10-07 sweeps did |
| `echo=true` | Also send suite logs to the Console; FAIL lines then trigger Console Error Pause, which can leave Play mode paused (`ExitPlaymode` still works) |
| `cleanupLeaks=false` | Keep leaked root objects |
| `maxSeconds=S` | Stop starting new suites after S seconds; the report has `complete=false` and `resumeAfter`, and the TXT and summary print the full resume options |
| `after=<FullName>` | Resume: run only suites sorted after this one and merge into the existing report of the same mode. Refused unless that report is incomplete, `after` equals its `resumeAfter` or `currentSuite`, and `filter`, `seed` and `all` match; copy the printed `resume with ...` options. The report records `resumedFrom` |
| `writeBaseline=true` | Also write `Logs/TestRunner/static-baseline-proposed.json` |
| `allowStaleCode=true` | Run despite a `STALE_CODE` refusal |

**Result files** in `Logs/TestRunner/` (git-ignored by `/[Ll]ogs/`):

- `static-<play|edit>.json`: the full report (`JsonUtility`). It is written when the pass starts, before each suite (with `currentSuite` set to it) and after each suite, with `complete=false` and `resumeAfter` = the last suite with a result until the pass ends. If Unity froze or crashed, `currentSuite` names the suite that hung. Fields: runId, startedUtc, unityMode, sceneGameManager, seedBase, filter, all, after, resumedFrom, maxSeconds, codeLoadedUtc, durationMs, complete, verdict, resumeAfter, currentSuite, totals, newSuites, missingSuites, warnings, and per suite: status (`pass`, `fail`, `error`, `skipped`), skipReason, modeMismatch, countSource, passed, failed, noSummary, seed, durationMs, exception, failures, failureCounts, errorLogCount and samples, leaked, leakedCount, knownLeaks, singletonsCreated, restored, strayFiles and the baseline diff.
- `static-<mode>.txt`: overwritten with a `RUNNING` header when the pass starts, so an old result is never mistaken for the current one. At the end: a header with run id, mode, seed, scene GameManager, totals and verdict; one line per suite run, for example `FAIL  Tests.Combat.RapidShotTests  48/54  known 0  new 6  0.0s`; then the sections REGRESSIONS, STALE, NEW/MISSING, LEAKS and WARNINGS. Read this first.
- `static-<mode>.log`: every captured line, with a `### <suite>` separator per suite, written at the end (a `RUNNING` line until then). After a resumed run it holds only the suites of the last call.
- The summary's last line lists the files this call wrote; a refusal writes only the TXT.

**Baseline** (`tools/tests/static-suites.json`, versioned, outside `Assets` so it has no `.meta`): `{ "version": 1, "seed": 20261007, "suites": [ ... ] }` with one entry per suite: `type` (full name), `needs`, `skip` (non-empty text skips the suite unless `all=true`), `expectThrow` (an exception type name, for example `TargetParameterCountException` for CharmPerson, TST-001), `passed`, `failed`, `flakyFailures`, `knownFailures` (a list of `{ "match", "issue" }`, where `match` is an ordinal prefix of a failure label and `issue` an issue ID) and `notes`. The runner never writes this file; `writeBaseline=true` writes a proposal to curate by hand: new failure labels get the issue `TODO`, and an exception seen in the run becomes `expectThrow` with `TODO: issue ID for <Exception>` appended to `notes`. The loader warns about known failures with an empty or `TODO` issue, and about an `expectThrow` whose `notes` have no issue ID (or a `TODO`).

**Verdicts.**

- A suite is a REGRESSION when it throws without a matching `expectThrow`, or when its failures not explained by a known label exceed `flakyFailures`. Unexplained = the larger of (unmatched labels + labels beyond the cap) and (the suite's failure count minus the FAIL lines whose label matched, capped at the failure count). Failures without a FAIL line therefore count as unexplained; suites that print each failure twice (Crafting, Rod, Phase5) are not penalized.
- A suite with no baseline entry (NEW) that fails or throws counts as a REGRESSION too and is listed under REGRESSIONS with `(no baseline entry)`.
- It is STALE when a known failure was not seen, or when `expectThrow` is set and it did not throw.
- A drop in total assertions against the baseline counts is a warning.
- The pass verdict is REGRESSION, else STALE, else OK. It is `NO_BASELINE` when the file is missing (a malformed file is reported and the run continues without a comparison) and `REFUSED` when the pass could not start (see Refusals). NEW (discovered, no entry) and MISSING (entry, not discovered) suites are listed; a NEW suite changes the verdict only when it fails or throws.

### 3.1 Running suites through the Unity MCP

When the Unity MCP is attached to this project (check that `Application.dataPath` and the console paths it reports are under `F:/DNDPrototype`):

1. In edit mode, after script changes, call `AssetDatabase.Refresh();` and check `!EditorApplication.isCompiling` and `!EditorUtility.scriptCompilationFailed` in the next call.
2. Edit pass: `result.Log(Tests.Runner.StaticSuiteRunner.RunFromCommand(""));`.
3. `EditorApplication.EnterPlaymode();`. Entering Play mode reloads the domain; the next MCP call runs once Play mode has started. Character creation is enough, because suites build their own characters.
4. Play pass: `result.Log(Tests.Runner.StaticSuiteRunner.RunFromCommand(""));`. A full Play pass of the 87 Play-mode suites takes about 3 s (2.8 to 3.2 s on 2026-10-07) and the edit pass about 0.2 s, so `maxSeconds` is a safety net; if you set it, resume with the printed `resume with ...` options until `complete` is true.
5. Read `Logs/TestRunner/static-play.txt` (and the JSON for detail) with the Read tool.
6. `EditorApplication.ExitPlaymode();`. Suites leave static state behind, so do not play by hand, and never run the scenario harness, in a Play session that ran suites.

```csharp
using UnityEngine;
using UnityEditor;

internal class CommandScript : IRunCommand
{
    public void Execute(ExecutionResult result)
    {
        if (!EditorApplication.isPlaying) { result.LogError("Enter Play mode first."); return; }
        result.Log(Tests.Runner.StaticSuiteRunner.RunFromCommand("filter=BullRushRulesTests,RapidShotTests"));
    }
}
```

Notes:

- A filtered suite whose `needs` does not match the current mode is skipped (it shows in the `skipped` count only): run `edit` suites (CauseFear, Scare and the 10 TST-029 suites) in edit mode, or pass `all=true`.
- For a seed sweep, call `Run(new StaticRunOptions { Filter = "...", Seed = n })` in a loop in one `CommandScript` and collect `suites[i].failures`; 67 seeds of one suite take a few seconds.
- The MCP refuses some namespaces in a `CommandScript` (for example `System.Reflection`); call the runner's public API instead.
- `Unity_GetConsoleLogs` output is too large to read whole; the runner's files are the record.
- Enter Play Mode Options are off (full domain reload). Exit Play mode before editing scripts. Whether Unity recompiles an edit made during Play mode depends on the per-user preference *Script Changes While Playing*; on 2026-10-07 it did not, and the old code kept running. The runner refuses with `STALE_CODE` in that case.
- If Unity freezes in a suite (an endless loop, a stack overflow), the owner has to kill and restart it. Then read `currentSuite` in `Logs/TestRunner/static-play.json`, add a `skip` for that suite to the baseline with the reason, and resume with the options for `after=<currentSuite>` (same filter and seed); the runner warns that the suite has no result.
- `AssetDatabase.DeleteAsset` fails through the MCP ("User interactions are not supported").

### 3.3 Scenario harness seams

The scenario harness (section 3.4; the soak and fresh-session batches are section 3.5) drives real fights in Play mode. It relies on:

- `_Core/ScenarioHooks.cs`: inert static hooks (dice filter, attack, AoO, maneuver, threatened-cast, NPC cast, move, condition, combat-log and phase events, scripted AI turns, forced initiative head, input suppression). Raise sites and what each one covers are listed in [architecture/combat-and-grid.md](architecture/combat-and-grid.md#scenario-hooks-test-instrumentation). Install handlers through `ScenarioHooks.Safe` and `ScenarioHooks.SafeTurn` and fail the run when `ScenarioHooks.HookErrors` is not empty. Call `ScenarioHooks.ClearAll()` when a run ends. Leftovers are also cleared: Enter Play Mode Options are off, so statics survive leaving Play mode, and `Tests/Scenarios/ScenarioSessionGuard.cs` (editor only, `[InitializeOnLoad]`) restores fast mode and clears the hooks on ExitingPlayMode and EnteredEditMode; `StaticSuiteRunner.Run` does the same before a pass and adds a report warning when anything was still set.
- `_Core/GameManager.ScenarioHarness.cs` (editor only, `internal`): `Harness_IsReady`, `Harness_SetupPartyFromCreation` (returns a reason when level-ups queued by creation were left unapplied), `Harness_SetupPartySlot` (set BAB through `BaseAttackBonusOverride`, CHR-068), `Harness_DeactivatePartySlot`, `Harness_SpawnEnemies` (the squares given, through the game's spawn placement; a negative square gets the default layout; the runner then places exact actors with `MoveToCell`), `Harness_StartCombat`, `Harness_HaltCombat` (stops GameManager and TurnService coroutines, so run the harness on its own MonoBehaviour), `Harness_ResetWorld` (runs every step even if one throws and returns the failed steps; summons are destroyed at the end of the frame), `Harness_RestorePartyAfterCombat`, `Harness_DumpState`, `Harness_PendingPrompt` (the open AoO confirmation, ranged retarget, full-attack 5-ft choice or special-style submenu, else null), `Harness_CancelToActionChoices`, `Harness_OpenSpecialAttackMenu` (presses Special Attack and reports whether the menu opened; a selecting flag already set before the press is reported, never cleared), `Harness_PressSpecialAttackButton` (clicks the open menu's button for a maneuver type, refused when that button is hidden or disabled), `Harness_SelectSpecialAttack`, `Harness_SelectSpell`, `Harness_ApplySpellBuff` (a buff spell's effect through `ApplySpellBuff`, the effect step of a landed cast, without slot or action; pass a clone), `Harness_PendingAoO`, `Harness_AnswerAoO`, `Harness_PendingCounterTripDefender` and `Harness_AnswerCounterTrip` (the counter-trip prompt, CMB-079; `Harness_HaltCombat` and the combat reset drop an unanswered one). `Harness_ResetWorld` also releases every party, pool and summon grapple before the summons are destroyed: grapple links are static and outlive a halted fight (CMB-038), and without that a reused slot started the next job still grappling. Two editor-only read accessors back this: `CombatUI.Harness_IsSpecialAttackMenuOpen`, `Harness_FindSpecialAttackButton`, `Harness_OpenSpecialStyleMenuName`, `Harness_FindSpecialStyleOption` and `Harness_FindSpecialStyleCancel` (the open selection submenu, its option by label and its Cancel button; CMB-127, CMB-124), and `CharacterController.Harness_GrappleLinkHolders` (the static link table, read without ending any link). Both party setups reset a slot that held a character through `GameManager.ResetPCSlotForNewCharacter` (the same `ResetCharacterSlotForSpawn` the enemy spawns use, CRE-046) before `Init`: `Harness_SetupPartySlot` directly and `Harness_SetupPartyFromCreation` through `SetupCreatedCharacters`. So a party character of one job does not inherit the previous job's Power Attack, Fighting Defensively, Rapid Shot, readied counterspell, attack pool, AI maneuver memory, tags, trackers, mount, feint windows, turn state, spell effects or spellcasting component, and casters get a fresh `SpellcastingComponent`. The harness does not reset enemy pool slots itself: `Harness_SpawnEnemies` goes through `SetupEnemyEncounter` and `InitializeNPCFromDefinition`, which first calls `GameManager.ResetCharacterSlotForSpawn` (CRE-046, fixed 2026-10-08), so every spawned slot starts as a fresh controller: no trait, component, spell effect, grapple or mount link, tag, AI memory or profile of its earlier creature (the old profile is destroyed only when the GameManager created it, never one the harness assigned), and no other character's feint window, readied counterspell, remembered square, concentration or aura save immunity tied to it (the list is in [architecture/characters-and-creatures.md](architecture/characters-and-creatures.md#from-definition-to-live-combatant)). A slot left inactive by the reset keeps its last creature until it is spawned again, which the clean check does not look at. Since the fix a soak seed gives the same trace hash in a batch session as alone in a fresh session (seeds 21-40 checked, section 3.5). Being `internal`, they are reachable from the harness in Assembly-CSharp but not from an MCP `CommandScript`.
- `CharacterCreationUI.CompleteWithParty(party, flowSource)`: the end of Play Now! and Quick Start, callable with any non-empty party (returns false and changes nothing for a null or empty one).
- `Tests.Scenarios.ScenarioFastMode` (editor only, public): `Apply("fast")` sets timeScale 30, captureFramerate 30, maximumDeltaTime 1, uncapped frame rate, run in background, logs below Warning filtered and dice logging off; `Apply("watch")` is real time with every other saved setting back (logs and dice logging visible again); any other mode is refused. `Restore()` puts the saved settings back. QualitySettings (vSync) are never written, so nothing can leak into ProjectSettings. `StartProbe()` and a later `ProbeResult()` measure waits under fast mode; a mode the harness had already applied stays applied afterwards.
- **Silent stalls.** Console Error Pause pauses Play on any `LogError` or exception: when polling a run, check `EditorApplication.isPaused` and unpause (or turn Error Pause off before a run). The other stall is editor throttling when Unity is not focused (see the probe below).

**Fast-mode probe of 2026-10-07** (Play mode, editor focused, MainScene at character creation): every `WaitForSeconds(0.8f)` and every `WaitForSeconds(0.08f)` took exactly 1 frame (20 of each), and each frame advanced scaled time by 1.0 s (captureFramerate 30 x timeScale 30; maximumDeltaTime 1 did not clamp it lower). The 40 waits took 41 frames and 0.073 s of real time (about 1.5-1.8 ms per frame); the game ran at about 650 frames per second between MCP calls. Every scaled wait in game code therefore costs one frame, and anything paced by `Time.deltaTime` jumps 1 s per frame (poison secondaries, CMB-007). Settings were restored afterwards (timeScale 1, captureFramerate 0, maximumDeltaTime 0.333). That probe also set vSync, which fast mode no longer touches. A second probe of 2026-10-07 (after the seams review, the probe now counts frames with and without editor focus) gave the same numbers (41 frames, every wait 1 frame, 0.07-0.14 s real time), with fast mode applied by the probe and again with fast mode already applied by the caller (it stayed applied afterwards). Unity reported the editor focused on all 42 frames (`InternalEditorUtility.isApplicationActive`), so frame advance with the editor unfocused is still not measured and the `EditorApplication.QueuePlayerLoopUpdate()` fallback is untested: before relying on unattended runs, run the probe with Unity in the background and check `editorUnfocusedFrames` and the frame counts. In that session a `Debug.LogException` did not pause Play (Error Pause was off).

**Job phases** (per scenario, seed and repetition; `Start` only schedules the run, and the first job begins on the next frame on the runner's own coroutine): preflight (Play mode, a ready GameManager, the project path; refused with `needsFresh` after static suites in the same Play session or after a dirty job), boot once per Play session (`CharacterCreationUI.CompleteWithParty` with the Quick Start party, the real creation path; default Fighter, Rogue, Cleric, Wizard), reset and clean check (`Harness_ResetWorld`, then no active pool slot, every `NPCs` entry a pool slot (`CharacterController.IsEncounterPoolSlot`; before ENC-001 the check compared the list's length with the first job's, which a grown pool would break), no extra live controller, no area effect, the GameEventSystem subscriber counts of the first job, no hook left set; a failure ends the job as Contaminated and stops the run), seed (`Random.InitState(seed)`, HP mode Average), spawn and place, control, hooks (trace, invariants, dice filter, input suppression, log listener, fast mode), start (`Random.InitState(seed * 7919 + 17)`, `Harness_StartCombat`), monitor (every frame), halt (twice, a frame apart, CORE-003), finalize, cleanup (hooks cleared, world reset, party rest, and control, profiles, RNG, HP mode and fast mode restored; each step guarded on its own). The whole party is rebuilt every job, so repetitions start from the same state. An exception that escapes any phase ends that job as Exception with a result, runs its cleanup, marks the session dirty and stops the run, so status.json always reaches a final state. Only profiles the harness created are destroyed; an `ActorSpec.Profile` override should return a fresh `ScriptableObject.CreateInstance` (an asset, or an instance another controller uses, is assigned but never destroyed).

**Running it through the Unity MCP.** Never edit scripts or call `AssetDatabase.Refresh` while a run is going. Depending on Preferences > General > Script Changes While Playing (not checked on this machine), a recompile either stops Play mode or reloads the scripts in place; either way the run is lost, and the runner writes status.json with `"state":"interrupted"` and a summary with run verdict INTERRUPTED. Exit Play mode and start a fresh session. Do not run the static suites during a run either: `StaticSuiteRunner` refuses while a run is in progress, and a pass that slips through ends the job as Contaminated.

1. `bash tools/compile_check.sh`; in edit mode `AssetDatabase.Refresh()` so Unity compiles the change.
2. `EditorApplication.EnterPlaymode();` (a fresh Play session; never one that ran static suites).
3. In a later command: `Tests.Scenarios.ScenarioHarness.Start("smoke/*", "1-3", "repeat=2")`. Filter: comma-separated id globs. Seeds: `1`, `1-5`, `1,3,7`. Options (`key=value;...`): `mode=fast|watch`, `maxRounds=N`, `repeat=N` (compares the trace hash of each repetition per seed), `sweep=N` (seeds 1..N, aggregated per id), `record=dice`, `keep` (stop after the first job and leave the world for a human), `wallCap=seconds` (default the definition's `.WallCap(seconds)`, else 120). `ScenarioHarness.Start(def, seeds, options)` runs a definition built inline in the CommandScript with `Scenario.Define(...)...Build()`, with no new file and no recompile. `ScenarioHarness.List(filter)` lists the catalog. Start returns `runId`, `jobs`, `statusPath` and `summaryPath` (absolute paths), and `loadErrors` when a catalog source threw (its remaining scenarios are missing from the run); it refuses with `needsFresh: true` in a dirty session.
4. Wait without the MCP, with a bounded loop run through Monitor or a background Bash (a foreground `sleep` is blocked in the agent environment): `for i in $(seq 1 200); do grep -qE '"state":"(done|interrupted)"' <statusPath> && break; sleep 3; done`. status.json is rewritten at most once a second while the run makes frames, at every job boundary and at the end; every write carries `heartbeatUtc` and `frame`. A heartbeat older than about 15 s while the state is still `running` means a dead run (a crash or a stopped coroutine): exit and re-enter Play mode. Or call `ScenarioHarness.Poll()` (never waits; it also unpauses the editor). `ScenarioHarness.Abort(reason)` ends the current job as Halted after its cleanup and skips the rest.
5. Read `Logs/Scenarios/<runId>/summary.json` (or `ScenarioHarness.Result()`), then grep the JSONL files.
6. `EditorApplication.ExitPlaymode();`. `ScenarioSessionGuard` clears any leftover hooks and fast mode.

**Files written** (`Logs/` is git-ignored): `Logs/Scenarios/<runId>/<id-slug>__s<seed>[__r<rep>].jsonl` (one event per line), `summary.json` (run verdict, totals, per-id aggregate, per-job results with violations, expectation lines and notes, waiver hits and `unusedWaivers`, frames, frames per second and editor-focus counts; `notRun` with a `resume` filter and seeds when the run stopped early; `loadErrors`; `warnings`, run-level warnings such as a combat-log leak the sweep had to clean up, section 3.5), `status.json` (state, `heartbeatUtc`, frame, current job and actor, totals; `summaryError` if the summary could not be written), all written through a temp file and `File.Replace` with retries, and one line per run in `Logs/Scenarios/index.jsonl` (run id, verdict, filter, seeds, options, totals, and `warnings`, the count of the summary's warnings, when there are any).

**Trace events.** Every line has `seq`, `f` (frames since the job started), `r` (round), `t` (turn index) and `ev`: `meta`; `actor` (key, team, control, source, class, level, HP, AC, touch AC, BAB, Hit Dice `hd`, racial Hit Dice `racialHd`, base saves `baseFort`, `baseRef` and `baseWill`, position, size, speed, AI profile, weapon); `init` (order with roll, modifier, total); `round`; `turn_start` (actor, controller `ai`, `scripted`, `idle` or `ui`, and a snapshot of every actor: HP, nonlethal, position, sorted conditions, HP state, grappling, team); `turn_end` (action-economy flags and the snapshots that changed); `move` (from, to, movement type, squares); `attack` (die, total, modifier = total - die, AC, hit, damage, natural 20 and 1, threat, confirmation, AoO flag and trigger, flanking and its bonus, sneak attack, ranged, weapon, weapon damage dice `dice` and their roll `baseRoll` (0 on a miss; a confirmed critical's roll includes the extra dice), concealment miss); `aoo` (trigger: movement, maneuver, spellcast, standup, bullrush-move, ranged, item, pickup or other); `maneuver`; `threatened_cast`; `cast` (an NPC-path cast begins: caster, target, spell id and level; the PC pipelines are not hooked); `generated` (what a definition's `GenerateActors` produced, for example the DMG encounter); `cond`; `hp`; `nl`; `dice` (with `record=dice`, or whenever a force fired); `log` (combat log text without rich-text tags); `phase` (with `by`, the GameManager methods that set CombatOver); `step`; `note`; `decision`; `violation`; `watchdog`; `log-leak` (the combat-log leak sweep found a leak: root lines destroyed, when, and the panel's `holders` and `lines` when they were out of bounds, section 3.5); `end` (outcome and final snapshots); `expectation`; `verdict`. The trace hash is SHA-1 over every line except `watchdog` and `log-leak` events (both depend on frame timing), without the fields `f`, `rep`, `utc`, `gitHead`, `wallSec`, `mode` (fast or watch, so the two modes can be compared) and `diag` (the timing-dependent detail of a SoftLock or Timeout decision). The `meta` event's `harness` field is 4 since the actor event gained `hd`, `racialHd` and the base saves (2026-10-08, CRE-004; 3 from the attack event's `dice` and `baseRoll`, 2 from the `cast` event); compare hashes only between traces of the same harness version and code.

**Invariants** (a broken one is a `violation` event): `hp-bounds` (HP at most max plus temporary HP; HP state consistent with HP), `grid` (on the grid, in its square's occupancy, no shared square unless grappling, the two are still in the square a pin release left them in (the release ends the grapple and moves neither, PHB p.157, CMB-089, CMB-122; the allowance is granted only when a Pinned condition ends and neither creature grapples afterwards, so a grapple ended by an escape, which must move the escaper, gets none; it ends when either leaves that square), one of the two is helpless (PHB p.148) or one is a swarm (MM p.237 and p.316); grapple opponents at most 1 square apart, or their natural reach if larger, since a grappling creature takes no ordinary movement and the grapple's own move drags its opponents along, PHB p.156-157), `turn-structure` (turn start and end pair up, one turn per actor per round, rounds never go back, no turn for a dead actor), `no-act-when-down` (no attack or maneuver by a dead, dying, stable or unconscious actor; a disabled actor, at 0 HP or at negative HP with Diehard, may act. The threatened-cast hook fires after the AoOs the cast provoked, so a caster dropped by one of them correctly loses the spell; only a spell that still goes off with the caster down is flagged), `attack-math` (a natural 1 never hits, the flanking bonus is 0 or +2, hit agrees with total against AC unless a natural 20, concealment, a protection barrier or Deflect Arrows, which the trace recognises by its "deflected" note), `econ` (no full-round action when the turn started disabled or staggered, no 5-ft step plus other own movement, at most 4x speed; moves are reported per segment, so the squares are a lower bound. The bull rush follow and overrun moves arrive as ordinary moves, so the squares moved since the actor's last attack, AoO or maneuver are taken back when a bull rush or overrun event arrives; whether a follow after a 5-ft step breaks the step is not settled RAW and is not flagged), `aoo-budget` (AoOs since the threatener's last turn at most 1, plus the DEX modifier with `Combat Reflexes`), `prone-move` (no own move of more than 1 square while prone, CMB-074), `team-stable` (no team change without Charmed or Commanded), `no-errors` (a LogError or LogAssert from game code is a violation; an exception from game code ends the job as Exception, halted by the runner on the next frame because halting inside a log callback is unsafe. Origin comes from the stack trace: a frame under `Assets/Scripts/Tests/Scenarios/` or in `ScenarioHooks.cs` is the harness, already reported as `hook-error`; no `Assets/Scripts/` frame at all, as for editor windows or an agent's CommandScript, is foreign; both only add a job note), `combat-end-detected`, `combat-end-early`, `phase-after-combatover`, and `hook-error` (a harness handler threw; always an Error).

**Combat end.** The harness uses the game's own predicate (owner definition 2026-10-07): `CombatEndRules.IsOutOfFight` (`Combat/Core/CombatEndRules.cs`), read through `ScenarioChecks.IsOutOfFight`, `SideState` (which reads `GameManager.GetCombatEndSides`, the counts `EvaluateCombatEnd` uses) and the snapshots' `out` flag (`ScenarioChecks.IsDownSnapshot`). A creature is out of the fight when it is dead, dying or unconscious, with or without regeneration or fast healing. Unconscious covers stable, knocked out by nonlethal damage, the Unconscious condition, asleep (the Asleep condition alone, as a sleep arrow applies it, counts) and petrified (considered unconscious: PHB p.311, DMG p.301). A disabled creature stays in, at 0 HP (PHB p.145) or at negative HP with Diehard (PHB p.93; healing at negative HP keeps a Diehard creature disabled, not stable, since 2026-10-08). A side is out when every active member of that team (party, pool and summons) is out and it has an active member or had one earlier in the combat (a side whose last creature was removed is out). Because the harness reads the game's own predicate, `combat-end-detected` and `combat-end-early` catch a missing check, not a wrong predicate: `Tests.Combat.CombatEndRulesTests` pins the predicate case by case from the owner definition. When the game sets CombatOver, the outcome is Victory or Defeat from the side states (if neither side is out, the game ended combat early: `combat-end-early`). When a side is out and the game has not ended combat by the end of that turn, the harness records `combat-end-detected`, sets VictoryUndetected or DefeatUndetected and halts the fight itself. Since the game checks at every turn boundary (`NextInitiativeTurn`), both are now unwaived failures; the `cause=hp<=0` / `cause=unconscious>0` split of the detail went with CORE-011 and CORE-037 (fixed 2026-10-08). Two combat-end choices are pending the owner (CORE-038): a tie is a defeat, and a controlled creature counts for its own team.

**Watchdog.** SoftLock after 300 frames and 60 game-seconds without a new event (repeated identical log lines do not count); SkipChainRunaway when more than 3x the initiative count turns start in one frame (CORE-012; halted inside the turn-start handler); Stalemate when a round past MaxRounds begins; Timeout at the wall-clock cap; Paused on a second editor pause that no logged error just preceded (a human or debugger pause). A pause in the frame of a logged error, or the next one, is Console Error Pause: the runner unpauses it at once and only notes it, so waived errors stay usable whatever the Console toggle says. SoftLock and Timeout add a diagnosis to the job notes and the decision's `diag`: `Harness_DumpState`, the active Canvas objects whose names contain Prompt, Dialog, Confirm or Panel, and the last 20 trace lines. Contaminated mid-job when a static-suite pass ran or the hooks were cleared. A soft lock, a runaway, an exception, a contamination or a dirty reset marks the session dirty: later Starts answer `needsFresh` until a new Play session.

**Verdicts.** Error (SetupFailed, SoftLock, SkipChainRunaway, Exception, Paused, Timeout, Contaminated, or a hook error), Fail (an expectation without an XFail issue failed, or an unwaived violation), XPass (an expectation marked `ExpectXFail(issue, ...)` passed, so the issue may be fixed; reported loudly), XFail (only XFail expectations failed), Inconclusive (an expectation could not decide, or the job was aborted: outcome Halted), Known (only waived violations), Pass. A sweep aggregates per id, first match wins: Error, Fail or XPass if any seed had it; Pass if any seed passed; Known if any seed was Known; Inconclusive if every seed was; else XFail. Run verdict: INTERRUPTED (Play mode ended or scripts reloaded mid-run), ERROR (also when jobs were left without a result), LOADERROR (a catalog definition or source failed to load, so the run may be a subset; see `loadErrors`), FAIL, XPASS, NONDETERMINISTIC (a repetition's hash differed; the job's `firstDiffSeq` is the first differing line), ABORTED or OK. An OK run in which some id aggregated to Inconclusive (every seed undecided, so the run proved nothing for it) reads `OK (n inconclusive)`, and status.json and summary.json list those ids in `inconclusiveIds`: check it before trusting an OK, and widen the seed range for those ids.

**Waivers.** `KnownIssueWaivers.Global`: CORE-003 for `phase-after-combatover` (the CORE-011 and CORE-037 combat-end waivers were deleted when those issues were fixed on 2026-10-08). A definition adds its own with `.Waive(issue, invariant, detailRegex)`. Every run lists the waivers that never matched in `unusedWaivers`; delete a waiver that stays unused after its issue is fixed. Add an error-log waiver only after seeing the real message, always with its issue ID.

**Writing a scenario.** Put it in `Catalog/<Area>Scenarios.cs`; prefer typed steps over coroutine scripts; name each expectation after the rule it checks (for example "Flanking gives +2 and leaves AC unchanged (PHB p.153, CMB-001)"); pin branch-critical dice by context with `.Force(sides, value, ctxSubstring, count)` (DiceService contexts such as "Trip touch attack"; context-free `DiceRoller` dice can be forced only by sides, and the raw `Random.Range` sites of TST-033 not at all); keep expectations structural, since any added or removed `Random` call shifts every later roll. Confirm NPC ids with `NPCDatabase.Get` first. Dice contexts in use (grep `DiceService.D20("` for the rest): "Trip touch attack", "Trip Strength check", "Trip defense check", "Touch attack" (the grapple touch attack), "Grapple check" (every grapple check, both sides; ties go to the higher modifier), "Grapple opposed check (attacker)" and "(defender)" (moving the grapple), "Bull rush check", "Bull rush defense", "Disarm attack roll", "Disarm defense roll", "Sunder attack roll", "Sunder defense roll", "Overrun attack roll", "Overrun defense roll", "Counter-trip check" (the defender's check when it trips back) and "Counter-trip resist check" (the original tripper's). Weapon attack rolls, initiative and the Concentration check (`ConcentrationManager`, `DiceRoller.D20`) have no context. Where a branch rests on such a roll, write the expectation for every branch (for example: a damaging AoO foils the disarm, otherwise the target is disarmed), return `ExpectResult.Inconclusive` when the branch under test did not come up, and run a seed range: a sweep aggregates to Pass when any seed passed and none failed.

**Limits of AI-run party members.** They take the NPC turn path: its own turn-start order (CMB-075), no rage or bardic music ticks (CHR-069), no area spells, metamagic, summons, two-weapon fighting or flurry (AI-001, SPL-091, AI-055, AI-053); see [systems/PC_NPC_PARITY.md](systems/PC_NPC_PARITY.md) section 2. Prompts other than the AoO confirmation and the counter-trip prompt (the ranged retarget, the full-attack 5-ft choice, a special-style submenu, bull rush push and follow, Improved Grab, the disarm item choice, the dual-wield prompt; the touch-spell prompt is answered Cast Now by the Ui `Cast` step) are not answered yet and end a Ui job as a SoftLock (see Scripted steps). ### 3.5 Fresh-session batches and the AI-vs-AI soak

**Fresh-session batches** (`ScenarioBatchDriver.cs`, `[InitializeOnLoad]`). From edit mode, `Tests.Scenarios.ScenarioHarness.QueueFresh(filters, seeds, options)` queues one fresh Play session per comma-separated filter (seeds and options as for `Start`, applied to each) and enters Play mode. The option `perSession=N` is the driver's own: it also splits the seeds into sessions of N seeds (it cannot be combined with `sweep`). `keep` is refused (the driver leaves Play mode as soon as a run ends), and so is a project whose Enter Play Mode Options turn off the domain reload (the sessions would not be fresh). The queue (at most 50 entries) lives in `SessionState`, so it survives the domain reload of every Play-mode entry. A second `QueueFresh` in the same CommandScript appends to the same batch; once Play mode has started it is refused, and once the batch is idle it starts a new batch and drops the old results. In each session the driver waits for a ready GameManager (60 s at most), calls `Start`, and when the run ends (an Error outcome or an Abort ends it too) records the run id, verdict and summary path, pops the entry and exits Play mode; back in edit mode it enters Play mode again for the next entry. Leaving Play mode in the middle of a run (by hand or a crash) has the runner write its summary and soak rows at once, records that entry as INTERRUPTED and drops it; if entries remain, the batch pauses until `ScenarioHarness.ResumeQueue()` (or `ClearQueue()`), otherwise the batch's soak report is merged. A script recompile during a run (Recompile And Continue Playing) kills the run in a domain reload; after the reload the driver records the entry as INTERRUPTED in the same way and exits Play mode. A recompile on leaving Play mode (Recompile After Finished Playing) drops the pending Play-mode entry; after that reload the driver enters Play mode again for a queued, unpaused batch. `ClearQueue()` empties the queue and, with no run going, merges the batch's soak report.

Progress: `ScenarioHarness.Poll()` (field `batch`: the full state while entries are queued or running, afterwards a compact one with the batch id, the result and verdict counts, `warnings` (the sum of the runs' summary warnings, when any) and the report paths) or `Logs/Scenarios/batch.json` (state `queued`, `running`, `paused` or `idle`, the queue, `currentRunId`, `currentEntry`, `currentStatusPath` and the results; each result has `warnings`, its run's summary warning count, when there are any). batch.json is written only on changes, so its `heartbeatUtc` stands still during a long session; liveness comes from `heartbeatUtc` in the file at `currentStatusPath` (the run's status.json, written about once a second while a job runs): older than about 15 s while batch.json says `running` means the session has stalled or the editor is gone. A background loop can watch batch.json without the MCP; use an absolute path, because agent shells reset the working directory: `B=F:/DNDPrototype/Logs/Scenarios/batch.json; for i in $(seq 1 200); do grep -qE '"state":"(idle|paused)"' $B && break; sleep 3; done; grep -oE '"state":"[a-z]+"' $B | head -1`. The loop stops after 10 minutes without saying so: read the state it prints and start it again while that is `queued` or `running` (one job can take up to its wall cap, 600 s for the soak). A fresh session costs about 7 s of entering and leaving Play mode. Never edit scripts while a batch runs.

### 4.3 F12 Spell Testing Panel

`UI/Spells/SpellTestingPanel.cs` is added to the canvas unconditionally (`SceneBootstrap.cs:193`, no debug-build guard) and toggled with F12 (`Update`, line 92; key check at :94). It lists every `SpellDatabase` spell (placeholders shown with a darker background), filters by text and level, offers metamagic toggles, and keeps damage/save/SR counters.

`CastSpell` (line 1096) works only during a PC's turn (`gm.ActivePC` must be non-null; otherwise it logs "No active PC!"). Bypasses applied to that PC, so do not treat results as normal play:

- A non-caster temporarily gets a Wizard 10 class level and a `SpellcastingComponent` (`EnsureTemporaryCasterSetup`).
- +4 to the casting ability (`ApplyAbilityBoost`); `Update` restores it (and the temporary Wizard setup) once `GetTestPanelCaster()` returns null.
- `EnsureSpellAvailable` adds the spell to known and prepared lists regardless of class list or caster level, adds a slot at the spell's level if none is ready, sets `SlotsRemaining` to 99 and un-uses spent slots holding that spell.
- `GameManager.TestCastSpellFromPanel` (`_Core/GameManager.TestPanel.cs:38`) sets `_testPanelCastActive`, forces `CurrentPhase = PCTurn`, resets the `_pending*` fields, applies metamagic to a clone, and calls `BeginPendingSpellTargeting`. `OnCellClicked` falls back to `GetTestPanelCaster()` (`GameManager.CombatActions.cs:558`). Because `ActivePC` already requires `PCTurn` (`GameManager.cs:282-291`), forcing the phase has no effect in practice, and the class comment's claim that the panel works outside a PC turn is outdated (UI-021, UI-046 in [issues/UI.md](issues/UI.md)).
- While `_testPanelCastActive` is true, three checks are skipped: the arcane spell failure roll (`GameManager.TryRollArcaneSpellFailure`, `Spell/Resolution/GameManager.SpellCasting.cs:213`), the spell component pouch check in `PerformSpellCast` (`:1689`), and the Stoneskin diamond-dust inventory check (`:7151`).
- These bypasses do not apply to single-target, touch or self casts. `PerformSpellCast` calls `CleanupTestPanelCast` as its first statement (`:1634`), before the pouch check, its ASF roll (`:1837`) and the spell handlers run, so such casts roll ASF and need a pouch and material components exactly as in normal play. The ASF bypass does apply to area casts (`PerformAoESpellCast`, ASF roll at `:3675`) and to summon casts (`PerformSummonMonsterCast` and `PerformSummonSwarmCast` spend resources through `TryConsumePendingSpellCast`, ASF roll at `:114`), because none of these paths calls `CleanupTestPanelCast`. The area path has no pouch check at all.
- The flag can leak into the next cast. `CleanupTestPanelCast` has only two callers: `PerformSpellCast` and the cancel branch of `HandleAttackTargetClick` taken when a non-highlighted cell is clicked (`GameManager.CombatActions.cs:1099`). After an F12 area or summon cast the flag stays set until one of those runs. Until then every cast skips the ASF roll, including NPC casts (`GameManager.NPCTurns.cs:797` calls the same `TryRollArcaneSpellFailure`). The +4 boost and the temporary Wizard setup also stay on the test caster, because `SpellTestingPanel.Update` restores them only once `GetTestPanelCaster()` returns null. This comes from code reading and was not verified in Play mode (SPL-036 in [issues/SPL.md](issues/SPL.md)).

## 5. Manual scenarios

### 5.1 Aid Another

Code: `Combat/Maneuvers/SupportActions.cs` (a `partial class GameManager`; the file's `SupportActions` class itself is empty). No preset exists; use a multi-PC party (Play Now! + `test_2_goblins`) and move characters into the layouts below (read "Orc" as any enemy). Distances are Chebyshev squares, reach-aware via `CharacterController.ThreatensWith`. Equipping a longspear for case 2 was not checked; the Store or stash may have one.

Flow:

0. Open **Special Attack** and choose **Aid Another**. The main-panel Aid Another button is always hidden (`UI/Combat/ActionButtonPanel.cs:706-707`). The entry (`UI/Combat/CombatUI.cs:1171-1174`) reads `Aid Another (Standard)` or `Aid Another (<reason>)` with reason `Used`, `Pinned`, `No ally` or `No target`, and is disabled unless `CanUseAidAnother` passes. `OnAidAnotherButtonPressed` has a pinned-to-grapple-menu redirect, but it is not reached from this menu because `CanUseAidAnother` already rejects pinned characters.
1. If both an aid target and an adjacent sleeping ally exist, a picker offers **Aid Attack/Defense** or **Wake Sleeping Ally**; otherwise this step is skipped.
2. Select an enemy the initiator threatens with its equipped weapon.
3. Choose **Aid Defense (+2 AC)** or **Aid Offense (+2 Attack)**.
4. Select an ally who threatens that enemy with the ally's own weapon. Reach-weapon allies adjacent to the enemy do not qualify; unarmed or ranged-weapon allies count as threatening adjacent squares.
5. The log shows `Melee touch attack vs AC 10:` with roll, modifier (BAB + STR + size + condition penalty) and total; on a miss, `Aid Another failed (needed 10).` The standard action is spent either way.

| Case | Layout | Expected |
|---|---|---|
| 1 Adjacent | Fighter (6,5) longsword, Rogue (6,6), Orc (7,6) | Orc listed; choose Defense; Rogue listed. With Fighter at (5,5) instead, the menu shows `Aid Another (No target)`. |
| 2 Reach | Fighter (5,5) longspear, Rogue (7,6), Orc (7,5) | Orc listed (distance 2); choose Offense; Rogue listed. |
| 3 No ally in range | Fighter (5,5), Rogue (10,10), Orc (6,5) | After choosing the aid type: `No allies in melee range of Orc!`; back to the action menu, no action spent. |
| 4 Several enemies | Fighter (5,5), Orc1 (6,5), Orc2 (5,6), Goblin (10,10), Rogue (7,5) | Orc1 and Orc2 listed, not Goblin. Select Orc1: Rogue listed. |
| 5 Several allies | Fighter (5,5), Rogue (7,5), Wizard (6,6), Cleric (10,10), Orc (6,5) | Rogue and Wizard listed, not Cleric. |

Bonus checks: each successful aider adds a +2 entry and entries stack; the first matching attack consumes them (offense: beneficiary attacks that enemy; defense: that enemy attacks the beneficiary). Unused entries expire at the beneficiary's second turn start. The Character Sheet shows an "AID ANOTHER BONUSES" section only while bonuses are active (`CharacterSheetUI.AppendAidAnotherSection`). The AI never uses Aid Another: `AIBehaviorData.UseAidAnother` exists but nothing reads it.

### 5.2 Sleep

Code: `GameManager.ResolveSleepSpell` (`Spell/Resolution/GameManager.SpellCasting.cs:5023`). Automated coverage: `Tests.Combat.SleepSpellRulesTests.RunAll()` (definition, Asleep condition, wake helper, Aid Another availability; not the HD pool).

Setup: `sleep_spell_test` makes PC1 Archmage Theron (Wizard 20, only active PC) against skeleton_archer (1 HD undead, immune), goblin_warchief (2 HD), orc_berserker (3 HD) and human_cleric (5 HD, over the cap). Its prepared list fails (section 4.2), so cast Sleep from the F12 panel on Theron's turn. Immune and over-cap creatures are dropped silently; the `Candidates: N` count excludes them.

1. **HD pool.** Cast so the 10-ft burst covers all four enemies. Log: `HD Pool: N (4d4) | Duration: R rounds | Will DC D` and `Result: K target(s) asleep. Remaining HD pool: P.` Repeat via F12 (slots refresh); N stays within 4-16.
2. **Ordering and cap.** Lowest HD first; ties broken by distance from the caster, not the burst center. A target larger than the remaining pool logs `(X HD) exceeds remaining pool (P) — skipped.` HD are deducted before SR and the Will save, so a resisting target still uses pool. human_cleric is never affected.
3. **Wake on damage.** Damage a sleeper (lethal or nonlethal): `<name> wakes from taking damage.`; Asleep is removed.
4. **Wake Sleeping Ally.** Not possible in `sleep_spell_test` (single PC). Use Play Now! + `test_2_goblins`: Elara casts Sleep (F12) on a burst that includes Aldric or the cleric Theron (Sleep affects allies; elves, including Elara and Lyra, are immune; the ally needs 4 HD or less and gets a Will save, so retry if it resists). An adjacent PC uses Special Attack, Aid Another, then Wake Sleeping Ally. Expect a standard action spent, `<aider> shakes <ally> awake.`, and Asleep plus Unconscious removed.
5. **Duration.** 1 min/level = 10 rounds per caster level (200 rounds for Theron). Use a low-level caster and end turns until `⏱ <name> wakes as sleep duration expires.`
